# Design

full-self-working (fsw) is one local process that sells, quotes, delivers and learns on freelance marketplaces for one operator. This file is the contract between modules; AGENTS.md holds the rules every change keeps. A module marked with a later phase does not exist yet; the phase that builds it adds its section here.

## Decisions

Each paragraph names a choice, what it was chosen over and why; a change that reverses one rewrites its paragraph in the same commit.

**The operator's own Chrome, on a machine the operator keeps on.** fsw reads and writes every marketplace through its web pages, in the Chrome the operator already signs in to, through the BrowserSkill extension in a window of its own, and runs as one supervisor process that a scheduled task starts (Scheduling). The alternative was a hosted server driving a browser of its own. The founder's brief asked for this machine and his signed-in browser, and the reason holds for any operator: the logins, including the Google sign-ins several platforms use, already live in that browser, so every message leaves from an account and device the platform already knows, while a hosted browser would need every login again and would act from a device the platform has never seen. The cost is that fsw works only while that machine is on and Chrome is open.

**The model writes the words; code sets the amount.** The model drafts each reply and quote and rates the job's size against a typical one within a fixed range (`quote.complexity`, 0.6 to 1.6). Code turns that rating into the amount from the price guide or the price row, clamps it to the row's floor and ceiling, and takes the deposit split from the payment settings (Economics); the gate refuses a draft whose amount still leaves the row's range (Policy gate). The alternative was letting the model price from the conversation. An amount the code sets traces back to market samples and the cost of the hours behind it, and moves only through settings and decided quotes, so no customer sees a price nobody can explain.

**One outbox, one authorize, one deal state machine.** Every outbound item is an outbox row, every send decision is one `authorize` call, and only `src/deal` writes job, quote and payment state. The first build, kept on `archive/20261026-151909`, sent from four places, kept approvals as files beside the ledger, wrote job status from five modules, and could press send and crash before recording it, which left a sent message the ledger did not know about. Now a row's status moves only by compare-and-set and a send counts only once it is read back on the page, so an interrupted send is settled by reading the page, never by sending again (Outbox).

**Codex runs every model turn.** Every model turn runs through the Codex CLI (`src/brain/codex.mjs`): signed in with a ChatGPT account it spends the subscription rather than API credit, it checks each answer against a JSON schema, and a turn that may write files runs in its sandbox, which keeps writes inside the job folder and blocks the network. A recipe whose steps fetch public pages, today `recipes/data_crawling.json`, sets `"network": true`, and its turns keep the write sandbox while `sandbox_workspace_write.network_access=true` lets the fetch through (measured 2026-10-27 with codex-cli 0.164.0: EACCES without the key, success with it). The sandbox also refuses npm's default cache under the user profile (EPERM on `AppData\Local\npm-cache`, measured 2026-10-28), so each workspace-write turn gets `npm_config_cache` in its own temp folder, which the sandbox allows and the turn removes. npm installs into the nearest folder holding a `package.json`, so the data crawl's build step writes `scraper/package.json` before it installs; without one npm walks up to a parent the sandbox refuses.

**Work that passed its checks is reviewed by another model family.** Before the operator approves a delivery, a model from a family the builder did not use (GPT, Claude or Gemini) reviews it (Work), since the review exists to catch what the builder missed; a same-family or unknown pair is recorded as an error, never as a pass. The review is a read-only codex turn, so it spends the same subscription as the rest and returns a schema-checked verdict. Its gap: the default builder is an OpenAI model, so a fresh instance has no other family to review with until `jobs.review.model` names one its codex reaches, which takes a proxy such as opencodex.

**Personal data lives only in the instance folder.** The repository is for any operator, so it holds code, descriptors, recipes and placeholder examples, and everything about one person (profile, business registration, payout account, ledger, customer threads) lives in the instance folder git ignores (Instance). Every choice one operator makes is a setting with its default in `src/core/config.schema.json` rather than a constant (Settings), and the privacy scan fails a tracked file that holds a value from the instance.

**fsw renders and deploys no operator site.** fsw is a commons every operator runs, so the repository holds nothing about one operator, neither data nor presentation: a page about one operator (a portfolio, a landing page, a brand) reads that operator's data from their own repository and design system and is built and deployed there, under that site's own rules. The alternative, retired on 2026-10-27, was a portfolio gallery in `site/` that `scripts/publish.mjs` deployed every day at 00:00, which put one operator's look, copy and hosting in a repository every operator clones. fsw's portfolio ranking (Portfolio) now serves the kmong gig images it writes (`src/listings/images.mjs`, designed in `docs/LISTING-DESIGN.md`). Its gap: a paid job whose client granted portfolio use is kept in the instance's portfolio (`portfolio/items.json`) and told to the operator only through the delivery notice that asks them to record the answer; it reaches the operator's site only through that site's own rules, which can refuse client work, and nothing in fsw publishes it. The README captures `src/portfolio/media.mjs` takes for authored repositories without media fed only that gallery, since the gig images take image media alone; they stay until a surface reads them or the portfolio job stops taking them.

**A paid quote is sent only when its expected value clears zero and the day's pace allows it.** The first v0 capped quotes by count, which stopped quoting at 72% of the cash cap while requests waited unread, and lifting the count without a value test would have spent the cash on whatever arrived first. `judgeQuote` in `src/economics/quote-gate.mjs` now judges each paid request quote: the win chance starts at the platform's equal share 1 / (quotes on the request + 1), because the arm posterior was empty (every soomgo arm stood at 0 wins and 0 losses), and blends with the arm's resolved outcomes at the current price basis, weighted by `minCases`; the margin is the seller net after fees minus the row's cost floor; the value is the chance times the margin minus the quote's cash cost. A fit under `quoteGate.minFit`, an unknown fit or value, a full request or a value at or under zero drops, and every verdict is a `quote.judged` event. `paceSpent` holds a request unread while the day's quote cash runs ahead of `maxCashPerDay` times the elapsed share of the Seoul day (`quoteGate.pace` even), the budget-pacing shape of arXiv 1506.05851 and arXiv 2503.06942, so one burst of requests cannot spend the morning's cash. The alternatives were a count cap, kept out for the failure above, and a model-estimated chance, kept out because nothing recorded would back it. The supply report counts the day's verdicts by reason and the pace holds, and the digest prints them in one line (Lead supply).

## The loop

Per enabled platform, one surface session per tick: confirm the login (a surface with `publicSense` keeps sensing when the login fails), sense the list rows (money fields go to the deal state machine), triage each row, read and decide and authorize and plan at most MAX_THREADS_PER_PLATFORM opened threads, apply the deal effects, then drain the outbox inside the outbound hours with read-back, so a deposit request from a hire seen in this tick is drained in the same tick; six failed polls in a row notify once. An item parked from its list row (closed, past the reply window, or labelled with a service the catalog does not hold or the instance does not answer there) waits until a newer message arrives or the settings it was parked under change (the services the instance answers, the reply windows, how the platform's labels map onto the catalog, or the platform's `quoteGate`), which checks it again from its list row; a paid quote the value gate dropped was already read, so a changed setting reads and judges it again. An item a pass already read (observed at night, or decided with nothing to send) keeps the list time it covered the same way, so a platform notice that moves the list time past the newest stored message does not send it through the model on every tick; a night read holds only for night ticks, so the first tick inside the outbound hours still decides. Daily and hourly jobs keep their ids in `run/state.json` lastRuns.

## Triage

`triage(inbound, ledgerRow, {mode, now, settings, descriptor, openOutbox, parkKey})` decides each list row from the row and the ledger alone: `wait` (unchanged since the last pass, or an outbox message or quote still `planned`, `awaiting_operator`, `approved` or `sending` holds the thread), `park` (an unread platform notice, a closed request, a message past `pipeline.replyWindowHours`, a label outside the catalog or a service `settings.answered` leaves out; counted as `thread.system`, `thread.skipped` or `thread.operator`), `observe` (observe mode) or `open`. A park and a read carry the list time and the settings key they were made under (`meta.skipped`, `meta.settled`); a thread whose pass threw is passed again while `meta.failed.count` is under `THREAD_ATTEMPTS` (3) and nothing went out since. `awaitingReply` is derived: newest message inbound, nothing observed after it, inside the window.

## Authorize

`authorize(item, ctx)` is the one decision on whether an outbound item may leave, composed in this order: a paid quote on a buyer request without the value gate's send verdict that the loop step stamps on its payload (`payload.gate`) is `refuse` unless the operator approved it (`gate.unjudged`), so a row planned before the gate never goes out unjudged; the gate with its slop lint (an approved text that fails it is `refuse`), mode and outbound hours, what the model decided (unsupported, label mismatch, a service no longer answered, needsOperator, a stage after the hire while `orders.watched` is false, confidence under `pipeline.minAutoConfidence`), operator-only kinds (`pay_request`, `delivery`), the price row, a stated budget under the cost floor (`budget.below_floor`) and the Seoul day's cash caps. An operator approval answers every decision rule. `mode.observe`, `hours.closed`, `budget.cash` and `budget.pace` are holds: the verdict is `send` and the outbox leaves the row as it is. `budget.pace` holds an unapproved paid quote at send while the day's quote cash runs ahead of the Seoul day (`paceSpent`, the check the loop makes before opening a request), so a quote planned earlier and retried later waits planned and uncharged. A cash quote refused only by the day's caps is held with nobody asked and goes out on a later day's budget; one no day can pay (no caps, an unread cost, a cost over the cap) goes to the operator. `operatingMode(configMode, {forceMode, now, instance})` is the one reading of the forced mode and the outbound hours for both the loop and `authorize`. Pacing stays in the driver guard; the drain treats `FSW_PACING_LIMIT` as a refusal before the page.

## Outbox

Statuses move only along `TRANSITIONS` (`src/outbox/plan.mjs`): `planned` to `awaiting_operator`, `sending`, `blocked` or `stale`; `awaiting_operator` to `approved`, `rejected` or `stale`; `approved` to `sending`, `blocked` or `stale`; `sending` to `observed` or `unobserved`, or back to `planned` or `approved` when the surface refused before the page; `unobserved` leaves only by the operator (`fsw approve <id> --sent` or `--reject`). Each change is a compare-and-set with one `outbox.status` event. `drain` first reads back every `sending` row and never sends it again (a quote and a proposal have no read-back and go to `unobserved`), then screens planned rows (`operator` to `awaiting_operator` with an approval id, `refuse` to `blocked`) and sends the rows `authorize` lets go now, oldest first, claiming each with the compare-and-set; the first cash quote the day cannot pay holds every newer one. A row is `observed` only on an observed receipt, and only then is the outbound message written and the deal signal returned. A quote the surface pressed but could not confirm keeps `receipt.pressed` and counts against its day's caps until settled. Before a row is screened the drain checks that its stored payload still hashes to its key (`keyMatches`, with the import's formula for a row imported from an approval file) and blocks one that does not as `payload changed after planning`. Each surface write carries a token from `src/core/authz.mjs`: `{key, digest, mac}` over the row key and the exact text sent, signed with a secret that lives only in the drain's process, which `authorizedSend` checks against the platform, thread, kind and text before anything reaches a page; a pay request also needs `approved`. Only `src/outbox` mints one (`scripts/check-imports.mjs`).

## Deal

`advance(ledger, signal, ctx)` is the only writer of `jobs.status`, `quotes.status`, `payments`, `reviews` and `money_events`, one transaction per signal, and returns effects (`plan_outbox`, `close_outbox`, `start_run`, `record_case`, `sync_portfolio`, `notify`) the loop carries out after the commit. A job opens at `quoted` from the first observed quote; a hire or an escrowed order moves it to `ordered` (on soomgo with a deposit request for the operator); a paid deposit starts the run, or for an operator-delivered service hands the job to the operator (`in_progress` with the balance request as the schedule-the-sessions item); `run_started`, `run_accepted` and `run_failed` come from the job child; `handoff_done` comes from `fsw job handoff <id> <step> [file ...]`, which copies the files into `jobs/<id>/handoff/<step>/`, and the delivery (with the balance request) is planned only once every user-handoff step of the last run that declares `produces` (a build, a URL file, an import report) is recorded with its files, or without files when its `when` condition does not hold; it carries those files, and its approval reason lists the steps that produce nothing for the operator to confirm there; `delivery_observed` makes it `delivered`, asks the client for portfolio permission and names the operator's `fsw deal` verbs for the answer and the review; a settled job closes (`job_closed` case, portfolio sync); a first revision request reopens it. A portfolio answer is decided before a revision in the same message moves the job. The model labels it granted, conditional (any limit on what, where, how or when the work is shown) or refused, quoting the client's sentence; `src/loop/permission.mjs` then holds a grant by default: it counts only when its quote is a whole sentence of a client message sent after the latest delivery and after the last answer, that sentence is an unconditional yes, and every other client sentence since the delivery is a plain yes, a known thank-you or sign-off, or logistics with no request, preference or restriction, which keeps the check fail-closed for wordings no list names. Anything else goes to the operator once (`permission.unverified`); a conditional or a refusal is recorded on every job of the thread that was ever delivered and holds through revisions and redeliveries, a condition never replaces a denial, an answer that reaches no job is told to the operator as `permission.refusal_unapplied`, and only `fsw deal <jobId> permission granted` lifts a condition or a denial, printing what it lifts. Money signals are recorded once per key (a parsed order or review row by its own `evidence.key`, a review the operator types by its job, so a second entry corrects the one row), older than seven days as history, and a chat row still showing a recorded hire adds nothing. A signal the state does not accept is a `deal.refused` event. `sweep` re-derives the outbox effects a crash between the commit and the effect applier lost; `readiness` holds a delivery until its payment level is met and stales a payment request no longer due.

## Work

`runJob(jobId, ctx)` runs one paid job through its recipe with the codex runner it is handed, the deal's payment check and a report door, writes `jobs/<id>/brief.md`, runs acceptance with one retry and reports `run_started` and `run_accepted` (with the recipe's user-handoff steps) or `run_failed`; it writes no job status. `startDue` spawns paid and revision jobs up to `jobs.maxParallel` and never an operator-delivered one; `src/loop/job.mjs` is the job child's composition. The `viewports` check renders each html deliverable at every viewport of `VIEWPORTS` (320 to 1920 px, `src/render/viewports.mjs`), with captures named `<stem>-<w>x<h>.jpg`; a recipe that lists `widths` renders a fixed-width artifact, states why in `widthsReason` (`validateRecipe` requires it) and is checked only at those widths, 900 px tall.

Accepted work is reviewed before the operator sees its delivery: `reviewDeliverables` (`src/work/review.mjs`) runs one read-only codex turn on a model family other than the builder's (`jobs.review.model`, else `gpt-6.1-sol` for work another family built), shown the brief, the text deliverables inline and the images attached, and records `{verdict, findings, reviewed, hash}` on the run, the job and the delivery row. A same-family or unknown pair, a turn that fails, a file the review could not read or read only in part, and a delivery with no review are verdict `error`; a pass that names a blocker is `fail`. `resolve` approves a delivery only with a passed review of the bytes it holds now, or with the operator's stated reason (`FSW_REVIEW_NOT_PASSED`, `FSW_REVIEW_CHANGED`, and `FSW_REVIEW_UNREVIEWED` for a file the review never read), and stamps the hash of its files (`src/core/reviewed.mjs`); the drain blocks an approved delivery whose files changed since and tells the operator once.

## Loop step

`step(platform, ctx)` runs one platform pass: login; sense, with every list row's money handed to the deal; triage; while the Seoul day's budget pays no quote, a buyer request on a cash platform is left unread with no model call (`threads.budget`), and while the day's quote cash runs ahead of `maxCashPerDay` times the share of the Seoul day gone by (`quoteGate.pace` even) it waits the same way (`threads.pace`, one `quote.pace_held` event a request a Seoul day); read, decide and plan at most `MAX_THREADS_PER_PLATFORM` opened threads (a buyer request ruled unsupported plans nothing and counts as `thread.operator`; a paid quote on a buyer request is planned only when `judgeQuote` of `src/economics/quote-gate.mjs` sends it, every verdict is a `quote.judged` event, and a drop parks with a reason starting "gate: ", or "expired" for a full request, under the pass's park key); the deal effects; then the drain (outside observe mode) and the effects of what it observed.

## Ledger

`openLedger(path)` runs the migrations from `PRAGMA user_version` up, one transaction each; a migration that rebuilds a referenced table turns foreign keys off around its transaction and checks them before the commit. Version 4 adds the outbox and changes no older table, so the 2c77326 code opens a version 4 file.

| `messages` | id, thread_id, direction (in, out), body, attachments json, external_id, at, gate json; unique (thread_id, direction, external_id) |
| `quotes` | id, thread_id, platform, service, amount_krw, deposit_krw, balance_krw, scope json, delivery_days, cost_krw, status (sent, accepted, declined, expired), at |

| `payments` | id, job_id, kind (deposit, balance, full, milestone), amount_krw, channel, received_at, evidence |
| `reviews` | id, job_id, platform, rating, text, liked, at |

| `money_events` | id, key unique, platform, thread_id, job_id, event, amount_krw, at, applied, note, payment_id, evidence, recorded_at |
| `outbox` | id, key unique, platform, thread_id, job_id, kind (message, quote, pay_request, delivery, proposal), payload json {text, amountKRW, split, scope, deliveryDays, files, costKRW, threadRef, serviceLabel, thread, decision, priceRow; importedFrom on imported rows; the proposal, currency and review keys of later phases}, verdict json, status (planned, awaiting_operator, approved, sending, observed, unobserved, blocked, rejected, stale), reason, approval_id unique, operator json {resolvedAt, finalText, edited, resolutionReason; filesHash on an approved delivery}, receipt json, created_at, updated_at |

Every SQL statement on the outbox lives in `src/core/ledger.mjs`: `addOutbox`, `updateOutbox(id, patch, {from})` (with `from`, a compare-and-set on status that returns null when the row has moved), `getOutbox`, `outboxByKey`, `outboxByApproval` and `listOutbox({platform, statuses, kinds, threadId, jobId})`; only `src/outbox` and `importApprovals` call the two writers. The outbox key is `platform:threadRef:kind:sha1(text|amount|files)` of the planned item (`outboxKey`), so an item planned twice is one row. An operator edit stays on its row as `operator.finalText` with `operator.edited: true`, and the drain sends and reads back `operator.finalText ?? payload.text`; the key keeps hashing the planned text, so the brain planning the same draft again lands on the same row, and a revised draft is a new row. A payment row is written only from evidence. `importApprovals(ledger, dir)` turns each 2c77326 approval file into an outbox row keyed by approval_id (open to awaiting_operator, approved, rejected and dropped to rejected, sent to observed, expired to stale, blocked, unobserved; project_proposal to proposal) and reports a file it cannot map by name; a row still planned, awaiting_operator or approved whose file holds a final status follows the file with a compare-and-set and an `outbox.status` event (`reconciled`); a second run imports and reconciles nothing.

`events.at` is the time the writer acted for: a loop step stamps its events with the tick's `now` (`ctx.now`), so a replay or a test with an injected clock compares like with like, and every other writer stamps the real time. Write order is `id`, so a query for the newest event of a kind orders by `id`, never by `at`, and a query over a time window orders by `at`, then `id`.

## Surface

## Economics

Prices are market based. A (platform, service) row's market base comes from the newest summary and the seller's reviews of that service on that platform: under 5 reviews p25 + 0.35 (median - p25), 5 to 29 the median, 30 or more halfway to p75, so a service the seller is new to enters at the first tier and wins its first jobs, and price learning raises it from there (the founder's decision of 2026-10-27). A service's count is the ledger's reviews joined to their jobs' service; the rest of the platform's total, which names no service, counts only for an operator-delivered service (work the operator did before fsw kept a ledger) and never for an agent-delivered one. serviceFit multiplies it (strong 1.15, some 1.0, none 0.9). The cost floor is the smallest gross whose net after fees covers the standard package's agent hours at `yield.agentHourCostKRW` plus its operator minutes at `yield.humanHourValueKRW`; the base is the higher of the two, and a row is viable while its cost floor stays at or under the market ceiling. Packages are base, base x 2.2 and base x 4, rounded to 1,000 KRW. A request quote is the row's base (tier, fit and learned factor) times a complexity factor (0.6 to 1.6), clamped to the guide's minimum and maximum, moved toward the buyer's stated budget and never below the cost floor plus the quote cost; until 2026-10-27 it was the guide average times complexity, which sent a seller's first quotes for a service at the market middle, where a seller with no reviews of it was not hired. `splitPayment` gives deposit and balance below `payment.milestoneThresholdKRW` and milestones above it, through the mechanism the descriptor names.

`sampleMarket(instance, {platforms, samplers, withPage, loadFx, now, day, log})` samples every platform the config lists with the samplers and page opener it is given, retries a failed category once, stops a platform at its first bot challenge, converts foreign prices at the day's ECB rates or fails that platform by name, replaces only the pairs it read, carries pairs it could not read for up to `CARRY_DAYS` (7), and writes the day's files only when the summary changed. Each platform is read through its market engine (`config.market.engines.<platform>`, else the descriptor's `market.engine`, else `owned`; `attached` is the operator's Chrome for public pages, `archive` the newest Wayback capture dated by its capture time), at most `config.market.categoriesPerRun.<platform>` categories a run, stalest first, and an error marked final is not retried; `config.market.cadence.<platform>` puts a platform in the daily market job or the hourly slice. `answeredServices(config, platform)` is the list of catalog services an instance answers on a platform (`platforms.<id>.services`, null for every agent-delivered one), and `operatorDelivered(service)` marks a service the operator delivers, such as `lesson_tutoring`. A price guide that prints only its average prices at that average. `refreshPriceTable(instance, {adapterFor, ledger, day, log})` prices every platform with summary entries, moves each row by the quote results it replays from `ledger` (price learning, below), and writes a new table only when a row changed; `latestTable(dir)` reads the newest. `catalogServicesFor(descriptor, label)` is the one mapping from a platform's label to catalog services.

`quoteResults(ledger, {asOf, expireAfterDays})` replays every quote fsw sent into one result: won (accepted), lost (declined, or the customer hired another pro, which the quote funnel saw on the chat list, cause `hired_other`), expired (no answer within `priceLearning.expireAfterDays`, 14, or seen still unopened by a poll of its chat once the hours after which the platform refunds an unread quote have passed, descriptor `bidCost.unreadRefundHours`, soomgo 48, the funnel's `quote.unread` event, cause `unread`; a quote no poll observed stays open, since the funnel reads only the chat list's first page), superseded (still sent on a thread whose deal moved on to another quote, neither won nor lost), refused (the platform refused the send before the client saw it) or open, each with the price index it went out at when its pricing basis is known: the amount over complexity times the row base before learning it was priced from. A request quote priced from the guide average has no index, since the factor now multiplies the tiered base, and counts in the win rate only. `learnPriceRows` moves a row's base by one factor per (platform, service), folded over its decided quotes oldest first: a win steps toward its index, a loss or an expiry steps under it and never up, by `priceLearning.step` (0.2), bounded to 1 plus or minus `maxMove` (0.3) and then between the cost floor and the market ceiling. Every decided quote counts in the win rate, but the factor moves only once `minCases` (5) decided quotes with a pricing basis fall inside `lookbackDays` (180); packages, floor and ceiling stay on the market. The allocation weighs an arm by its win rate times the net of a win from the learned base, less its quote cost per quote.

The quote funnel (`src/loop/funnel.mjs`) reads soomgo's chat list on every poll and writes change-only events (`quote.opened`, `quote.hired_us`, `quote.hired_other`, `quote.hired_other_cancelled`, and `quote.other_status` for a hire status the code does not name, kept raw and told to the operator once) linked to the fsw quote of the row's request; a newer quote on the request starts the chat's record over. `quoteFunnel` counts one platform's quotes of the last seven days as sent, opened, hired us, hired another pro, no answer yet and chats not linked to an fsw quote; the hourly supply report and the 09:00 digest print that line, saying opens are not recorded yet until a chat row has reported one.

## Scheduling

All marks are Seoul time and aligned to minute 0, and the 13 job ids of `src/supervisor/schedule.mjs` are the `lastRuns` keys of `run/state.json`, unchanged from 2c77326 and 9101c1c so a takeover reads the old state as it is, less `publish`, retired in writing on 2026-10-27 with the portfolio site (Decisions); an old state's `publish` key stays in the file and is never read, since a job is due only by its own id. Every 5 minutes: `poll`, one loop step per platform in draft or auto mode, because marketplaces rank sellers by response time and a buyer request closes after its first few quotes; then `orders`, which applies the effects a crash lost (the deal's `sweep`) and starts paid and revision jobs within `jobs.maxParallel`. Hourly at :00: `hourly` (supervisor self-check, the read pass on observe platforms, the lead supply report and the review count watch, which reads inside the hour's read share, tells the operator once per new review, and once a Seoul day when a platform's counts went unread for 24 hours), `projects` (크몽 엔터프라이즈 projects, since a project stays open for days and its proposal quota is per day), `listings` (kmong review results) and `market-hour` (the market slice of hour-cadence platforms, one Fiverr search). Daily at 00:00: `market`, `price`, `allocation` (no arm for a service the instance does not answer there), `portfolio`, `listings-refresh` (gigs whose top items changed, and the kmong career figure; skipped and kept due under a forced observe pass) and `learn`. Daily at 09:00: `digest`, which opens with the lead supply section. A job is retired only by the founder in writing.

The supervisor is one process started by a per-user scheduled task at logon and re-checked hourly at :00; a pid lock prevents doubles. It keeps the BrowserSkill daemon alive as a child, which ends with the supervisor that started it, so every tick with due jobs checks the keeper before its first job and a supervisor that took over after a code change starts its own daemon at its first tick. The keeper holds every daemon child it started until that child exits and ends each on stop; a status read that times out while the daemon's named pipe listens is a busy daemon, kept and reported (the hourly job reads it as partial), never a missing one; and `fsw run` exits with the supervisor's code 5 s after it returns, logging the handles that still held the process. It holds a Windows execution-state request so the machine does not idle into sleep, runs platform pipelines concurrently with one tab per platform, and runs jobs as separate processes up to `jobs.maxParallel`. Outbound actions respect `activeHours` and each descriptor's pacing (minimum gap between page loads, maximum actions and messages per hour).

`fsw run` and `fsw tick` share the pid lock at `<instance>/run/supervisor.pid`: one process per instance drains the outbox, so a tick takes the lock for its pass or exits 1 while a live supervisor holds it. At start, before its first tick, the supervisor imports the approval files the 2c77326 code wrote (`importApprovals`) and logs the result. A tick that wakes less than a second before the mark it slept toward runs at that mark. A platform that signed out is signed in again from the file `logins` names (an email login per platform, or `{method: "google"}` for a Google sign-in with the email of the identity file `onboarding.identity` names, kept outside the repository) through the surface's `signIn`, at most once an hour, keyed on the last `platform.sign_in` event, which records only whether it worked; a Google sign-in that fails asks the operator once per platform while that request is open. Every line of `supervisor.log` is `<ISO time> <text>`: `supervisor pid <n>`, `approvals import read <n>, imported <n>, already <n>, reconciled <n>, skipped <n>`, `tick <job>:<status> ... failures=<n>`, `code moved from <a7> to <b7>; restarting` and `supervisor exiting for a restart` or `supervisor stopped`; the `supervisor.tick` event names the commit the process runs (`code`).

A process keeps the modules it loaded, and agents edit the main checkout all day, so the scheduled task runs the supervisor from a detached worktree of `main` (`%LOCALAPPDATA%\fsw\code`, or `FSW_CODE_DIR`) that only ever holds committed code and never runs npm, so nothing `src/cli/run.mjs` loads may import a package (`scripts/check-imports.mjs`). After each tick the supervisor compares that worktree with `main`; when `main` moved and the new commit's module graph imports in a temporary worktree, it checks the commit out and exits with code 75, and the launcher starts it again at once. A commit that does not import is reported once and the running code stays. The launcher restarts a supervisor that crashed after five minutes, and the config is read again every tick, so a setting changes at the next mark without a restart.

A takeover of the live line, and a way back from it, run only through tracked scripts, each read-only unless given `--apply` or its write flag. `scripts/takeover-check.mjs` confirms that local `main`, the deploy worktree and the expected commit agree, that the lock holder is a live supervisor (its start time when the lock records one) and the task runs, that no gap between ticks since a given time (the newest tick before it included) passes a limit, and that `supervisor.log` holds exactly the handovers, restarts and approval imports expected; it also fails when two or more ticks of the expected code ran and every one failed its poll, or when its newest STUCK_POLLS ticks all did, since counting ticks alone passed a night on which every poll failed. `scripts/ledger-snapshot.mjs` takes one consistent read of the ledger beside a record of its hash, integrity, version and table counts, checks a ledger against that record, and restores a snapshot only inside the instance it names while no supervisor runs and the task is stopped, keeping the replaced file with its WAL under names SQLite opens. `scripts/approvals-writeback.mjs` writes the outbox outcomes back into the approval files the 2c77326 code reads, planning every file before it writes any and refusing while a supervisor runs, so the old code never sends an item v0 already sent and still holds the items v0 planned. `scripts/rollback-takeover.mjs` stops the task and the lock holder, writes back, moves `main` to the old line with a compare-and-swap, starts the old line and waits for its first tick; until the write-back and the move both finished it restarts v0 instead and exits 2, since starting the old code over stale files would send twice. `scripts/rehearsal-effects.mjs` proves that a rehearsal on a copy of the instance sent nothing. The takeover of 2026-10-26 moved `main` from the 2c77326 line (kept as `archive/20261026-151909`) to v0 with a compare-and-swap, ran the rollback once as a drill and moved forward again, recorded the ledger event `takeover`, and replaced `origin/main` with a lease; from then on `main` moves only by fast-forward to `v0`.

## Portfolio

`src/portfolio/rank.mjs` is the one ordering of portfolio items; the listing images and every listing generator import it. An item is shown when it is a background project, or a paid job whose client granted portfolio use, and never when it is rated under 4 of 5 or marked disliked. The order follows the founder's order of satisfaction, fame, quality, volume and recency:

1. Tier A (liked, or rated 4.5 or more) comes before tier B.
2. Tier A orders by liked, fame, quality, volume.
3. Tier B orders by fame, quality, volume.
4. Volume compares the price first and the hours second; ties fall to the newest `paidAt`, then the id; a missing value sorts after a present one.

Fame is a client's fame on a paid job, else the item's public reach that day: GitHub stars and npm downloads of a repository or package the operator authored (created, owns and made the first commit of), each on a log scale against the largest of the instance's own items (`src/portfolio/signals.mjs`); a contribution to another maintainer's repository has none. Quality is the share of viewports at which the item's live page renders with no overflow and no broken image. The daily portfolio job reads both once per Seoul day, keeps no figure whose source went silent, and captures a README image (`kind: 'readme'`, never a gig image) for each authored repository without media (`src/portfolio/media.mjs`).
